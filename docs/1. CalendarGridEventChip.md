   2. CalendarTimeGrid.kt:188 — replaceable with a custom PageSize + fill modifiers

  It reads maxWidth only to compute columnWidth for PageSize.Fixed, and maxHeight only to pin gutter/strip heights. Both are layout-time computable:

  - columnWidth: PageSize is an interface that receives availableSpace at measure time. The pager sits after the gutter in the Row, so its available space is already maxWidth - calendarHourLabelWidth:
  
  private class DayColumnPageSize(private val daysToShow: Int) : PageSize {
      override fun Density.calculateMainAxisPageSize(availableSpace: Int, pageSpacing: Int): Int =
          availableSpace / daysToShow
  }
  - viewportHeight: the gutter and each CalendarDayStrip sit inside containers that already have the viewport's height, so Modifier.fillMaxHeight() replaces .height(viewportHeight), and fillMaxWidth() replaces
  .width(columnWidth) inside a page (each page is exactly one column wide).
  
  That removes the subcomposition wrapping the entire grid. Caveat worth checking on device: with PageSize.Fixed the page width is a stable Dp; with integer division in a custom PageSize you get px-exact
  columns (actually better — no sub-pixel seams), but verify the pager's pageForDate scroll targeting still lands cleanly.
 
 3. CalendarMonthView.kt:156 — legitimate use, but hoistable
 
  Here constraints genuinely change what composes: chipCapacity drives how many chip lines exist and the "+N more" labels via monthWeekBarLayout. A plain Layout can't feed a measured size back into composition
  — that's exactly what subcomposition is for. So keep BoxWithConstraints, but note it currently runs once per composed page (~3 subcompositions) even though every page gets identical constraints. Since
  WeekdayHeaderRow renders the same locale weekday sequence on every page, you can hoist it above the HorizontalPager and wrap the pager in a single BoxWithConstraints, computing rowHeight/chipCapacity once
  and passing them into pages.
